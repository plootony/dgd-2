# Архитектура и соглашения DGD

## Основание

Правила опираются на официальную документацию Godot:

- [Организация сцен](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html): самостоятельные сцены, небольшие классы с одной обязанностью, передача зависимостей извне и связь через сигналы. Документ прямо перечисляет SOLID, DRY, KISS и YAGNI.
- [Организация проекта](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html): группировать связанные сцены и ресурсы; использовать `snake_case` для файлов/каталогов и `PascalCase` для узлов; отделять сторонние дополнения.
- [Стиль GDScript](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_styleguide.html): `snake_case` для переменных и методов, `CONSTANT_CASE` для констант, `PascalCase` для классов и ссылок на классы; сигналы описывают произошедшее событие. Отступ — табуляция; свойства идут перед методами.

Это рекомендации движка. Приведённое ниже распределение обязанностей — решение для этого проекта, а не обязательная структура любого Godot-проекта.

## Структура

| Каталог | Ответственность |
| --- | --- |
| `game/` | Точка входа, сборка зависимостей, игровая сессия, стандартные действия ввода |
| `world/` | Геометрия тестового полигона, свет и обзорная камера |
| `characters/` | Общий контракт персонажа, контроллер игрока, контроллер зомби и временная модель Tony |
| `combat/` | Попадания, здоровье, сетевое состояние боя; отдельная реализация регдолла |
| `weapons/` | Вид от первого лица, подготовка клипов и ресурсы параметров оружия |
| `network/` | Версия схемы комнаты и настройки сессии |
| `ui/` | Меню/HUD, настройки графики, сетевой монитор |
| `tests/` | Проверки поведения и тестовые сцены/контроллеры |
| `tools/` | Инструменты подготовки ассетов, например запекание анимаций |
| `docs/` | Документация; `.gdignore` исключает её из импорта |
| `addons/` | Стороннее расширение Fusion |

Импортированные модели, анимационные библиотеки, оружейные исходники и их внутренние имена костей/клипов сохраняют исходные пути. Новые собственные файлы именуются по правилам выше; сторонние ассеты не переименовываются ради косметики.

## Обязанности и зависимости

`game/main.gd` соединяет меню с действиями сессии, создаёт арену, передаёт корень мира настройкам графики и назначает контейнер трупов персонажам. Игрок не записывает себя в `current_scene.local_player`: локального игрока назначает создавший его контроллер сессии.

`ui/game_ui.gd` создаёт виджеты и обновляет представление. Нажатия превращаются в сигналы запросов; UI не подключается к Photon и не создаёт персонажей. `world/test_arena.gd` строит полигон, его освещение и подключает запечённую навигационную сетку.

`characters/combat_actor.gd` содержит общую настройку компонента боя, приём сетевого состояния, скрытие/восстановление тела и создание регдолла. Наследники отвечают за свой ввод, движение и точку возрождения. Метод `get_eye_position()` — общий контракт, поэтому бою не нужны поля `net_crouched`, `third_person` или `camera` конкретного игрока.

`combat/combat.gd` получает тело, репликатор и функции положения глаз/возрождения через `configure()`. События `died` и `respawned` сообщает сигналами. Компонент не ищет главную сцену, не создаёт графику и не управляет камерой. Рейкасты выполняются в физическом цикле. Проверка полномочий Fusion остаётся частью сетевого боя.

`characters/zombie/zombie_controller.gd` управляет преследованием и последовательностью крик → удар → восстановление. Сцена `characters/tony/tony.tscn` задаёт временную модель и максимальное здоровье. Урон, смерть и возрождение используют общий компонент боя; специальной проверки имени Tony в нём нет. Состояние и время начала действия передаются одним снимком, анимация воспроизводится локально. Подготовка анимаций и навигации вынесена в `tools/`; подробнее — [zombies.md](zombies.md).

`weapons/weapon_definition.gd` описывает данные оружия. Ресурсы `definitions/ak74u.tres` и `definitions/beretta.tres` задают урон, темп стрельбы, режим огня, положение модели, точки прицела и исходные клипы. Каталог используется и боем, и первым видом: длительность выстрела не дублируется. `weapon_animations.gd` подготавливает анимации; вид оружия управляет их воспроизведением.

## SOLID, DRY, KISS на практике

- **SRP:** сборка мира, UI, движение, бой, физика трупа и обработка клипов разделены по причинам изменения.
- **OCP:** параметры и разметка клипов нового оружия добавляются ресурсом и записью каталога. Новый тип персонажа предоставляет контракт глаз/возрождения, не добавляя проверок имени NPC в бой. Назначение новой клавиши и новый тип анимации при необходимости требуют обычного изменения кода.
- **LSP:** общий контракт персонажа доступен игроку и Tony; код боя не предполагает наличие камеры у каждого участника.
- **ISP:** компонент боя получает только нужные ему зависимости; меню сообщает намерения сигналами.
- **DIP:** зависимости между сценами связывает их создатель. Глобальный поиск через `current_scene` не используется игровыми компонентами.
- **DRY:** параметры оружия и общая обработка жизни персонажа имеют одно место определения. Несколько похожих строк, выражающих разные правила движения, не объединяются искусственно.
- **KISS/YAGNI:** один уровень общего наследования и обычные дочерние узлы. Нет DI-контейнера, глобальной шины событий, ECS или универсальных фабрик без конкретной необходимости.

## Именование и изменения

- Собственные каталоги, `.gd`, `.tscn`, `.tres`: `snake_case`; имена файлов описывают роль.
- Именованный класс: `NetworkPlayer`, файл: `network_player.gd`. Узлы: `PlayerSpawner`, `Corpses`.
- Методы и поля: `get_eye_position`, `corpse_parent`; внутренние детали: `_queue_shot`.
- Константы значений: `MAX_HEALTH`; ссылка на тип через `preload`: `WeaponCatalog`.
- Сигналы: `shot_fired`, `died`, `respawned`; запрос действия: `offline_requested`.
- Использовать явные типы на публичных границах, ранние выходы и небольшой размер методов. Форматирование — `gdformat` из `gdtoolkit==4.5.0`.
- При переносе скрипта переносить и `.gd.uid`, обновлять ссылки в сценах, ресурсах, инструментах и тестах. `.godot/` — восстанавливаемый кэш, не исходник.
- Имена RPC, пути свойств `FusionReplicationConfig` и порядок оружия в каталоге — часть протокола. При несовместимых изменениях менять `ROOM_PREFIX`/`GAME_MODE` в `network/session_config.gd`. После этого старые и новые клиенты не смешиваются в одной комнате.

## Проверки

Из корня проекта, заменив `godot` путём к Godot 4.7.2:

```sh
godot --headless --editor --import
godot --headless --path . --script res://tests/test_weapon_actions.gd
godot --headless --path . --script res://tests/test_combat.gd
godot --headless --path . --script res://tests/test_scene_composition.gd
godot --path . --script res://tests/test_scene_composition.gd
gdformat --check game characters combat weapons world network ui tests
```

Последний запуск Godot использует настоящее окно для проверки захвата мыши, движения и меню. В headless-режиме этот же тест проверяет независимость сцен и сигналы UI; движение с захваченной мышью пропускается.

Сетевой тест — два процесса в отдельной уникальной комнате; сначала `host`, затем `client`:

```sh
godot --headless --path . --script res://tests/test_combat_network.gd -- --room=unique_test_room --role=host
godot --headless --path . --script res://tests/test_combat_network.gd -- --room=unique_test_room --role=client
```

Сетевые тесты требуют доступ к Photon. Физика костей остаётся локальной косметической симуляцией; движение доверено владельцу. Рефакторинг не добавляет lag compensation, античит или синхронизацию каждой кости.

Проверено 10 сентября 2026: форматирование 23 скриптов, оба оружия, локальный бой/регдоллы, независимое создание персонажей, UI и движение в X11, два клиента Photon (обе стороны завершили сетевой тест с нулём ошибок).
